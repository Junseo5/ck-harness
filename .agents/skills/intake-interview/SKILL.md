# intake-interview

목표: 코드를 쓰기 전에 "무엇을, 누구를 위해, 어떤 기준으로" 만드는지 확정할 재료를 모은다.

## 1. 파악 (코드 작성 금지, 10분 이내)
1. 작업 폴더 구조와 과제 문서(README, 안내문)를 읽고 다음을 5줄로 요약한다.
   - 산출물 형태(웹 화면, API, 리포트, 기존 코드 수정 등)
   - 사용자와 사용 장면
   - 명시된 요구사항 / 명시되지 않았지만 필요해 보이는 것
2. 데이터가 있으면 파일별로 행 수, 컬럼, 결측·중복·이상값, 대표 샘플 2개를 요약한다.
   데이터가 크면 사람에게 `explorer` 서브에이전트 사용을 제안한다(직접 띄우지 않는다).
3. 실행 환경을 확인한다: 언어·런타임 버전, 의존성 설치 가능 여부, 기존 테스트 유무.

## 2. 명확도 점검
목표 / 판단 기준과 예외 / 제약 / 성공 기준을 각각 0(모름)·1(대략)·2(확정)로 매긴다.
가장 낮은 항목부터 질문을 만들고, 답을 받을 때마다 점수를 갱신한다. 모두 1 이상이면 합의 단계로 간다.

## 3. 질문 사다리 작성
아래 순서로 질문 후보를 단계마다 1~2개 만든다. 데이터에서 발견한 이상한 점은 업무 질문으로 바꾼다
(예: "상태값이 비어 있는 건 12건인데, 현장에서는 이걸 어떻게 처리하시나요?").

1. 현재 방식: 지금은 이 일을 어떻게 하는가
2. 최근 사례: 최근에 실제로 있었던 한 건
3. 사용 장면: 결과물을 언제, 누가, 무엇을 보고 쓰는가
4. 판단 기준과 예외: 포함/제외/확인필요를 가르는 기준
5. 제약: 시간, 형식, 보안, 성능, 바꾸면 안 되는 것
6. 빠진 주제: 내가 묻지 않았지만 중요한 것
7. 합의: 오늘 범위와 성공 기준 요약 → 확인 요청

규칙
- 질문은 한 메시지에 하나. 처음 몇 개 질문에는 해결책 단어(대시보드, API, 모델 등)를 쓰지 않는다.
- "무엇을 하면 될까요 1·2·3" 같은 떠넘기기 질문 금지. 내가 이해한 내용을 먼저 말하고 확인을 구한다.

## 4. 출력
- 요약 5줄 + 데이터 요약 + 명확도 점수 + 질문 사다리 목록을 보여준다.
- `docs/COLLAB.md`에 질문 후보를 미리 적어 두고, 사람이 담당자 답을 알려주면 `답`과 `결정` 칸을 채운다.
- 다음 단계 제안: 합의가 끝나면 `$plan-gate`.
