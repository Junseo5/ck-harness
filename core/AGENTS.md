# AGENTS.md — 이 작업 폴더의 맥락

사람(리드)이 판단하고, AI 세션은 위임받은 일을 한다. 아래는 이 과제에서 무엇이 중요한지에 대한 맥락과, 그동안 잘 통했던 작업 방식이다.
세션은 하나여도 여러 개여도 된다. `bin/dev`·`bin/analyst`·`bin/reviewer`로 켜면 그 관점 소개가 더해지고, 그냥 켜면 한 세션이 모든 관점을 오간다.
스킬(`.agents/skills/`)은 각 단계에서 쓸 수 있는 작업 방법이다. 상황에 맞으면 골라 쓰고, 사람이 `$이름`으로 부르면 그 방법을 따른다.
대회·과제별 맥락은 이 파일 끝의 "이벤트" 섹션에 있다.

## 1. 폴더
| 관점 | 실행 | 주로 다루는 곳 |
|---|---|---|
| dev | `bin/dev` | `src/`, 테스트, 실행 설정, README |
| analyst | `bin/analyst` | `docs/COLLAB.md`, `docs/PLAN.md`, `docs/DECISIONS.md` |
| reviewer | `bin/reviewer` | `verify/`, `docs/VERIFY.md` |
- `docs/`는 모든 세션이 함께 쓴다. 다른 세션도 고칠 수 있으니 고치기 직전에 다시 읽는 편이 안전하다.
- 검증은 구현과 따로 계산해야 의미가 있다. 같은 로직을 따라 하면 같은 버그를 함께 갖게 된다.
- 세션 여럿이 코드를 나눠 맡으면 `docs/PLAN.md`에 세션별 폴더를 적어 두면 서로 덮어쓰지 않는다.
- `explorer` 서브에이전트는 읽기 전용 조사(데이터 점검, 로그 분석, 결과 요약)에 맞춰져 있다.

## 2. 이 과제에서 잘 통하는 방식
- 요구가 애매하면 추측보다 담당자에게 물을 질문으로 정리하는 편이 결과가 정확하다. 담당자 답이 평가 근거가 된다.
- 요구를 충족하는 가장 단순한 구현이 유리하다. AI 평가는 요구에 없는 계층·설정·옵션·방어 코드를 감점 요인으로 본다.
- 작업 기록 전체가 평가 자료다. 실패나 미완성은 그대로 보이는 편이 낫다. 예외를 삼키거나 테스트를 약하게 만들면 더 크게 드러난다.
- "됐다"고 할 때는 방금 실행한 명령과 출력이 근거가 된다. 실행하지 못한 것은 "미확인"이라고 적어 두면 사람이 판단하기 쉽다.
- 데이터를 거르거나 분류할 때는 `입력 = 포함 + 제외 + 확인필요`가 맞는지 보면 해석 오류를 일찍 잡는다.
- 큰 데이터·로그는 개수·요약·샘플로 보면 토큰과 시간을 아낀다.

## 3. 보고
짧은 보고가 사람에게 읽기 쉽다. 예:
```
변경: <파일 목록>
확인: <실행 명령> → <결과 요약>
위험: <남은 문제·가정, 없으면 "없음">
```

## 4. 문서 (docs/)
PLAN(계획·세션별 폴더) · COLLAB(요구 문답) · DECISIONS(결정·버린 대안·AI 제안을 바꾼 지점) · VERIFY(검증).
인수인계(실행·결과·한계·다음 할 일)는 프로젝트 README에 쓴다. 결정과 문답은 생길 때 짧게 남겨 두면 서술형 답의 근거가 된다.
`.harness/`는 작업 도구(역할 소개·스크립트·템플릿)라 결과물과 섞이지 않게 둔다.

## 5. 환경
- 원격·컨테이너 환경이라 서버는 `0.0.0.0`에 바인딩해야 미리보기에서 보인다. 포트는 PLAN에 적어 둔다.
- 비밀값(API 키·토큰)은 이 과제에 필요 없고, 코드에 들어가면 감점과 보안 문제가 된다.
- 단계마다 한국어 메시지로 커밋하면 작업 이력이 설명 자료가 된다: `feat:` `fix:` `docs:` `test:` `chore:`.
- 빌드·서버를 동시에 여러 개 띄우면 메모리가 모자라기 쉽다. 끝난 서버는 종료한다.

## 6. 스킬 (흔한 진행 순서)
| 스킬 | 쓰기 좋은 때 | 주 관점 |
|---|---|---|
| `$intake-interview` | 시작 직후: 과제·데이터 파악, 질문 정리 | analyst |
| `$plan-gate` | 범위가 보일 때: PLAN 작성과 점검 | analyst |
| `$slice-implement` | 구현 단계마다 | dev |
| `$verify-loop` | 기본판이 돈 뒤: 독립 검증·두 단계 리뷰 | reviewer |
| `$risk-audit` | 기능을 굳힐 즈음: 약점 정리·설명 예행연습 | reviewer 또는 dev |
| `$handoff` | 마감 전: README 인수인계 | dev |
| `$submit-check` | 제출 직전 점검 | dev |
시간 기준점과 제출 절차는 이벤트 섹션에 있다.
