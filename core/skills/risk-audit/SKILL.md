# risk-audit

이 단계에서는 코드를 고치지 않는다. 치명적인 결함을 찾으면 보고만 하고 사람이 결정한다.

## 1. 약점 목록 (docs/HANDOFF.md의 "한계와 위험"에 기록)
최대 6개, 영향이 큰 순서로. 각 항목은 다음 3가지를 한 줄씩:
- 약점: 어느 파일·함수의 무엇이 (예: `src/rules.py`의 `classify()`가 날짜 형식 오류를 제외로 처리)
- 영향: 어떤 상황에서 누가 무엇을 잘못 보게 되는가
- 다음 검증: 무엇을 어떻게 확인하면 되는가

살펴볼 곳: 가정으로 처리한 판단 기준, 예외 처리, 개수 대사, 입력 형식 의존, 성능·규모, 보안(입력 검증, 비밀값), 테스트가 없는 경로.

## 2. 설명 예행연습
형식(문항 수, 분량, 발표·서면 여부)은 AGENTS.md 이벤트 섹션의 "설명 예행연습 형식"을 따른다. 없으면 질문 6개.
`git log --oneline`, `docs/COLLAB.md`, `docs/DECISIONS.md`, `docs/VERIFY.md`를 근거로 평가자가 낼 법한 질문을 만든다.
유형을 섞는다: 설계 이유, AI 출력을 그대로 쓰지 않고 바꾼 지점, 특정 함수의 동작 예측, 약점과 위험, 검증 방법, 요구 변경 시 수정 범위.

질문마다 답안 뼈대를 짧게 준다(사람이 자기 말로 다시 쓸 수 있게). 기본 4문장:
1. 결론 (파일·함수 이름 포함)
2. 근거 (요구한 사람의 답, 데이터, 검증 결과)
3. 한계
4. 다음 검증

## 3. 출력
약점 목록과 예상 질문을 보여주고 `docs: 위험 정리` 로 커밋한다.
