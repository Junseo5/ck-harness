# verify-loop

검증 결과는 `verify/`와 `docs/VERIFY.md`에 남긴다. 검증하면서 `src/`를 직접 고치면 독립성이 사라지니, 고칠 것은 지적으로 남긴다.

## 1. 기준 확보
- `docs/PLAN.md`의 성공 기준, `docs/COLLAB.md`의 판단 기준과 예외를 목록으로 뽑는다.
- 기대값은 `src/` 로직과 따로 만든다(따라 하면 같은 버그를 함께 갖는다). 비교 대상은 결과물(출력 파일, API 응답, 화면)이다.
  `src/`는 4번 코드 품질 점검에서 읽는다.

## 2. 검증 스크립트 (하나만)
- 프로젝트 스택에 맞는 뼈대 하나만 복사해 채운다:
  `cp .harness/templates/check.py verify/check.py` 또는 `cp .harness/templates/check.mjs verify/check.mjs`.
- 원본 입력에서 기대값을 직접 계산하고, 결과물과 비교해 항목별 PASS/FAIL을 출력한다.
- 검증 코드도 짧을수록 좋다: 확인 항목당 몇 줄. 검증용 프레임워크는 이 규모에 과하다.

## 3. 확인 항목 (요구와 데이터에 실제로 있는 것 위주)
1. 개수 대사: 입력 = 포함 + 제외 + 확인필요
2. 핵심 규칙 표본: 기준별 대표 사례 몇 건을 손으로 계산한 값과 비교
3. 경계값: 판단 기준의 임계값 정확히·바로 위·아래. 데이터에 그 값이 없으면 임시 입력 2~3건을 만들어 결과물에 넣어 본다(원본 데이터는 바꾸지 않는다).
   빈 입력·중복·형식 오류·결측은 데이터에 실제로 있거나 요구에 언급된 것만.
4. 인터페이스: 서버가 있으면 실제 요청(`curl`)으로 상태 코드와 응답 형태 확인

## 4. 두 단계 리뷰
1. 요구 충족 (먼저): PLAN 성공 기준·COLLAB 판단 기준을 하나씩 대조. 빠진 요구, 잘못 해석한 요구, 요청하지 않은 추가 기능.
2. 코드 품질 (1단계 통과 범위에서만): 조용히 틀린 결과를 내는 경로, 예외 삼킴, 하드코딩된 기준, 비밀값, 바인딩, **과한 설계**(요구에 없는 계층·설정·방어 코드). 취향 문제는 생략.
지적은 위치(파일:함수) / 문제 / 근거 / 영향 / 제안, 심각도 순으로 중요한 것부터.
제안은 요구 범위 안의 최소 수정으로 한다. 요구에 없는 대비(가상의 입력, 미래 확장)는 수정 제안 대신 "위험"으로만 기록한다.

## 5. 기록과 보고
- `docs/VERIFY.md` 표에 항목/방법/기대/실제/판정을 채운다.
- FAIL은 재현 명령과 함께 구현 쪽에 넘길 한 줄 요약으로 남긴다.
- 판정할 수 없는 것은 "담당자 확인 필요"로 남기고 질문 문장을 만든다.
- `test: 독립 검증 추가` 로 커밋하고 3줄 보고(변경/확인/위험).
