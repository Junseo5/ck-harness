# slice-implement

## 시작 전
- 이번에 할 단계 번호와 산출물을 PLAN에서 찾아 한 줄로 말한다. 단계가 지정되지 않았으면 묻는다.
- 바꿀 파일 목록을 먼저 말한다. `verify/`와 다른 세션이 맡은 폴더는 건드리지 않는다.

## 구현
- 그 단계에 필요한 최소한만 만든다. 다음 단계 코드를 미리 쓰지 않는다.
- 업무 기준은 이름 있는 상수·함수로 둔다 (예: `MIN_STOCK = 10`, `classify_order()`).
- 데이터를 거르거나 분류하면 개수 대사를 출력하거나 테스트로 확인한다.
- 서버는 `0.0.0.0` 바인딩.

## 확인 (완료 주장 전 증명)
- 보고 직전에 확인 명령을 다시 실행하고 출력을 읽는다: 테스트, 스크립트, 서버라면 `curl` 응답. 가능하면 `bash .harness/smoke.sh`.
- 보고에는 명령과 출력 핵심 줄을 넣는다. 실행하지 못했으면 "미확인". "될 것이다" 같은 추측형 완료 금지.

## 실패했을 때 (디버깅 4단계)
1. 재현: 에러의 핵심 줄을 읽고 재현 명령을 확정한다.
2. 비교: 동작하는 경우와의 차이(입력, 환경, 최근 변경)를 찾는다.
3. 가설: 원인 가설 하나를 말하고 그것만 확인하는 최소 변경으로 시험한다.
4. 수정: 원인을 고치고 재발하지 않음을 명령이나 테스트로 보인다.
같은 문제로 3번 실패하면 구조 문제로 보고 멈춘 뒤 선택지(범위 축소, 다른 방식, 담당자 확인)를 보고한다.

## reviewer 지적을 받았을 때
- 항목마다 코드와 요구에 비춰 맞는지 먼저 확인한다. 맞으면 고치고, 틀리면 근거와 함께 반박한다.
- 영향이 큰 것부터 하나씩 고치고 매번 확인한다.
